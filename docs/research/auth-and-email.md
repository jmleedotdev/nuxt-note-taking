# Authentication and transactional email research

**Research date:** 2026-11-02 (UTC). **Status:** planning/interview input, not an approved architecture or implementation plan.

Only primary sources were used: maintainers' documentation, release metadata, and upstream source. Sources were fetched over HTTPS with `curl`/Python because no dedicated browser/search tool was available in this research session. Security-sensitive implementation observations below use those release tags, not assumptions from older tutorials. Recheck and pin versions before implementation. [S1][S2][S3]

## 1. Recommendation

**Prefer Better Auth + its Drizzle PostgreSQL adapter for the initial TypeScript backend, with database-backed sessions and verification/reset records, and an application-owned HTTP contract.** It supplies substantially more of the required account lifecycle than Nuxt Auth Utils. However, it is **not configuration-only compliance** with the accepted requirements: latest-reset-link-only behavior, the precise Unicode password policy, and leaving no active session after a password change require deliberate application logic. Approve the selection only with those gaps visible and a subsequent, separately authorized integration/security test gate. [S4–S12]

**Prefer Resend's HTTP API through its Node SDK for production**, especially if Vercel remains a hosting option. Use a small application-owned mail-sending boundary, and **Nodemailer → Mailpit for local email capture**. This is a recommendation for two environment-specific transports, not a claim that the Resend SDK can point at Mailpit's SMTP listener. If one SMTP transport in development and production is a stronger priority, Nodemailer can use a transactional provider—including Resend—in production. SMTP is a credible alternative, particularly on a persistent VPS, but provides no email delivery service by itself. [S18–S25]

**Supabase Postgres does not require adopting Supabase Auth.** Use it as managed PostgreSQL behind the Nuxt server and Drizzle, or use PostgreSQL on a VPS. Keep the frontend out of direct database access. Supabase Auth's verification/reset/SMTP settings would not configure Better Auth or a custom auth implementation. [S26–S28]

If a Laravel rewrite is near-term and definite rather than merely possible, revisit the first recommendation: Nuxt Auth Utils plus a deliberately small custom auth service gives more direct control over the persisted model, but transfers the complete security lifecycle to this project. Neither choice makes a Laravel rewrite automatic. Laravel already supports Resend and SMTP, so choosing Resend now does not force a later email-provider change. [S29]

## 3. Better Auth: configuration is necessary but not sufficient

### Persistence and revocation

- Use the PostgreSQL Drizzle adapter (`provider: "pg"`), generated auth tables, reviewed Drizzle migrations, and **`transaction: true` on the adapter**. PostgreSQL supporting transactions does not cause the adapter to enable them automatically; its inspected default is false. The Better Auth CLI can generate the Drizzle schema; schema generation is not the same as applying migrations. [S8][S12]
- Start with database-backed sessions, **no secondary session store**, and `session.cookieCache.enabled: false`. The session documentation expressly warns that cached cookies on other devices can remain usable until the cache expires. Database deletion cannot remotely erase another browser's cookie; authoritative validation on subsequent requests is the security boundary. [S5]
- For password reset, `revokeSessionsOnPasswordReset: true` plus enabled adapter transactions gives the documented database transaction path. Secondary storage weakens this: session removal there occurs after commit on a best-effort basis, and failure can leave sessions valid until expiry. Avoid introducing that topology without a separate revocation design. [S4][S7]
- For password change, the session guide's phrase “revoke all sessions” must be read alongside source: the default `revokeOtherSessions` path creates a fresh session. That is not “everyone must log in again.” Enforce the accepted policy on the server, including requests that omit or falsify the flag. [S5][S9]
- A hard seven-day limit is different from seven days since last refresh. Better Auth normally extends expiry after `updateAge`; use `disableSessionRefresh: true` for the conservative interpretation of the accepted maximum. Confirm whether later explicit reauthentication counts as a new session. [S5]

### Reset behavior requiring custom work

The current release has stronger single-use and transaction behavior than some older examples: it validates/hashes the proposed password, then consumes the token inside the reset transaction; the consume path also checks expiry. Do not repeat the unsupported claim that all Better Auth reset endpoints are merely non-atomic read/delete operations. Conversely, **single-use does not mean latest-link-only**: two different issued tokens have different identifiers and the stock issuance route does not invalidate the first when issuing the second. [S6][S7][S11][S12]

The additional behavior must serialize **issuance and redemption for the same user**, make only the latest authorization valid, and consume that authorization together with the password write and all-session revocation. A hook that merely deletes old rows after sending mail, or a client that requests a new token and then invalidates the old one, is not enough under concurrent requests. The concrete supported extension/custom-endpoint seam needs validation against the pinned release. Any stock auth route left reachable must enforce the same invariant or be deliberately blocked; an application wrapper alone does not close a bypass. This is custom engineering, not an advertised option.

The same review should examine a login racing a password change/reset: transactional deletion of existing sessions alone is not proof that an in-flight login verified against the old hash cannot create a session afterward. Use concurrency tests to decide whether additional per-user serialization/session-generation enforcement is needed.

### Verification behavior

Configure `emailVerification.sendOnSignUp` and `sendOnSignIn` explicitly, not from prose assumptions: the email/password guide says verification is sent on sign-in, while the options reference describes `sendOnSignIn` defaulting to false. Choose the resend behavior deliberately. Configure `autoSignInAfterVerification` explicitly as well. [S4][S10]

The inspected standard email-verification link is a signed, expiring JWT containing the email; the flow is not the same as database-backed reset tokens. It does not provide “newest verification link invalidates older links” or a consumed-token record by default. Already-verified users get an idempotent success path. Those are **not currently accepted requirements for verification**, so do not add custom single-use verification machinery without a decision. Default verification expiry is one hour. [S10][S16]

A Nuxt page redirect is only UI behavior. Server authorization must resolve the session, check verified status and scope every note/tag operation to the current owner. Nuxt UI does not supply this security policy. Better Auth's Nuxt integration demonstrates handler mounting, incoming-cookie forwarding and server route checks; its example session check must be extended for this app's verification gate. [S17]

### Password semantics

The accepted “Unicode characters” needs a precise counting rule. Recommendation: count Unicode code points, not UTF-16 units, bytes or displayed grapheme clusters; accept spaces including leading/trailing spaces and never call `trim()`. For example, eight supplementary-plane emoji count as eight code points but 16 JavaScript code units; a 128-code-point password may occupy 256 code units. Consequently the library's built-in limits must not reject valid input before the exact app validator runs. Validate every exposed password-writing entry point, including reset and any later set-password flow. [S7][S9]

Better Auth's default `@better-auth/utils` 0.5.1 Node implementation normalizes **NFKC before scrypt** and stores `salt:hex-key`. This is not trimming, but it changes some Unicode representations and even some space characters. The requirement does not settle normalization. Do not call the password byte-preserving or recommend a different normalization silently. Decide whether to retain documented NFKC or use an explicitly chosen alternative via custom hash/verify functions, then test signup/login/change/reset consistently. [S30]

For migration, “both use scrypt” does not establish compatibility: parameters, salt interpretation, encoded hash format, normalization and verification must match. Nuxt Auth Utils delegates hashing to AdonisJS's scrypt driver; it does not use Better Auth's `salt:hex-key` implementation. Laravel's documented built-in drivers are bcrypt and Argon2 variants, not a promise to verify either JavaScript library's scrypt encoding. A later migration needs a legacy verifier with rehash-on-login, a deliberately cross-runtime hash format from the start, or an explicit reset migration. Do not default to bcrypt merely for portability at the expense of the accepted long Unicode-password policy. [S14][S30][S31]

## 4. Nuxt Auth Utils: what custom persistence actually entails

Nuxt Auth Utils provides sealed-cookie sessions, session composables, password hashing and OAuth handlers. It is not a database account lifecycle framework. Its current v0.6.0 secret is derived from Nuxt's **`NUXT_APP_SECRET`**, which must be set in production; older advice to use `NUXT_SESSION_PASSWORD` is obsolete for this release. It requires a running Nuxt server, not `nuxt generate`. [S3][S13]

To meet the requirements, application code would own:

1. Users, credential hashes, verified state, provider identities, migrations, unique-account rules and ownership relationships to notes/tags.
2. Registration/login validation, credential checks, session creation and session-fixation prevention.
3. Verification tokens, expiry, resend, consumption policy, callbacks and all email delivery.
4. The 30-minute, single-use, latest-only reset lifecycle and transactional password/session updates.
5. A database session registry or checked generation scheme, per-session current logout, all-session revocation, absolute lifetime and cleanup.
6. Generic forgot responses, enumeration/timing review, atomic shared throttles, trusted proxy/IP interpretation, CSRF/origin protection and safe redirects.
7. Later Google callback persistence, local-account linking, verified-email policy and any token storage/refresh logic.

The session `fetch` hook is **not a universal authorization hook**. In the inspected implementation it is called by the session GET endpoint; `requireUserSession` directly calls `getUserSession` and tests for a user. Registering a database check only in the fetch hook would therefore leave protected API handlers that use the standard helper alone insufficiently checked. Make an application server guard authoritative on **every** protected route, and validate the session endpoint too. [S13][S15]

Similarly, clearing a sealed cookie is not server-side revocation of a stolen copy. Keep a session-specific authoritative database record, or an equivalent checked revocation model, and have logout revoke only that session. Rotating the global app secret is not an acceptable substitute: it disrupts all users and is not targeted current-session logout. The advantage of this option is control and a potentially simpler custom data model; the cost is owning and testing all of these security flows rather than only Better Auth's identified gaps.

## 5. Stable HTTP contracts and later Google/Laravel portability

**Recommended boundary, subject to approval:** the Nuxt UI calls application-owned HTTP endpoints and receives application-owned user/session/error shapes. Auth cookies remain HttpOnly; browser code does not depend on a provider token or decode session cookies. Hide Better Auth client calls or Nuxt Auth Utils composables behind that frontend boundary rather than spreading their endpoint names and response types through notes/settings components.

This still needs care:

- Wrapping `auth.api` on the server bypasses Better Auth's HTTP rate limiter. Apply shared limits at the public application routes, and preserve relevant origin/CSRF checks, incoming cookies, and **all Set-Cookie response headers**. Do not assume a server call automatically updates the browser. SSR cookie forwarding must be request-scoped. [S4][S17][S32]
- Keep the public API and auth callback on the frontend's origin through a reverse proxy if possible. A later cross-origin backend introduces cookie-domain/SameSite/credentials, CORS and CSRF decisions. Stable JSON contracts do not by themselves preserve cookie behavior.
- Stable app user IDs and provider subjects can migrate. Better Auth's schema, sealed cookie format, OAuth state, hash encoding and session middleware are not Laravel-native contracts. Prefer planned session invalidation at backend cutover unless session compatibility is separately engineered and tested.
- Laravel's default request normalization must be checked against **the actual contract field names**. Its trim middleware excludes `password`, `current_password` and `password_confirmation`; camelCase `currentPassword`/`newPassword` are not in that built-in exclusion list. A rewrite must preserve the no-trimming requirement rather than blindly adopting defaults. [S33]

### Google-specific details that are not interchangeable

| Topic | Better Auth | Nuxt Auth Utils / later replacement |
| --- | --- | --- |
| Callback route | Default documented callback is `/api/auth/callback/google`; changing auth base path changes it. | The application's handler route is the callback, e.g. `/auth/google`; `redirectURL` can be configured. Preserve a public callback or update Google's registered URI at cutover. |
| Protocol implementation | Current Google source uses immutable `sub`, default `email profile openid` scopes, and requires a PKCE code verifier for the authorization-code flow. It also supports separate direct ID-token sign-in. | Inspected v0.6.0 Google handler exchanges a code with client secret, checks state, and fetches the userinfo endpoint with the access token; default scopes are `email profile`. It does not construct a PKCE challenge/verifier or directly validate an ID token in that handler. Do not claim identical OIDC/PKCE behavior from the provider name alone. |
| Local identity/account linking | Persists user/account association. Implicit same-email linking is enabled by default when the provider verified the email or is trusted; `disableImplicitLinking: true` preserves explicit linking. | `onSuccess` receives user/tokens; application code must decide which local account owns that identity and persist it. Returning a profile is not an account-linking implementation. |
| Verification gate | `emailAndPassword.requireEmailVerification` does not apply to social login. Current per-provider `requireEmailVerification` is separate and gates local verified state. | Application decides how trusted Google `email_verified` maps to local verified state and enforces the same route guard. |

Sources: Google setup and Better Auth OAuth/account documentation and provider source; Nuxt Auth Utils Google handler. [S34–S37][S3]

Google requires exact registered redirect URIs. Store Google identity as provider + `sub`, linked to an application user ID, **not email as the immutable identity**. Decide whether Google's verified-email assertion satisfies this app's verification requirement and whether same-email users must explicitly link from an authenticated session. Recommendation: permit trustworthy Google verification, but require explicit linking to an existing local account rather than silent same-email attachment. Google access/refresh tokens are not the app's login sessions; ask only for sign-in scopes, do not request offline access unless a real Google API feature needs it, and do not copy provider tokens into public session JSON. These policies must be reproduced in Laravel, not left to each framework's defaults. [S35–S38]

## 6. Transactional email: package, transport and provider are separate choices

| Choice | What it is | What remains this app's responsibility |
| --- | --- | --- |
| Resend Node SDK (`resend`) | A client package calling **Resend's hosted HTTP email service**. Resend supplies sending infrastructure and delivery status facilities. | Server-only API key, sender/domain verification, templates/text fallback, delivery-error handling, abuse limits, dispatch lifecycle, and any retries. A successful API response is provider acceptance, not proof of inbox delivery. |
| Nodemailer + SMTP | A Node mail-composition/transport package connecting to **an SMTP server**. It is not a hosted sending provider. | Choose and configure an SMTP provider/relay, credentials, TLS, sender authorization, timeouts, error handling and dispatch lifecycle. The provider supplies delivery infrastructure. |
| Nodemailer + Resend SMTP | Both products together: Nodemailer is the client; Resend remains the provider. Resend documents its SMTP host, supported ports, username `resend`, and API key as password. | Same sending-domain requirement as the API. This is not provider independence just because the protocol is SMTP, although switching SMTP providers usually involves less transport-specific code. |
| Nodemailer + Mailpit | A local SMTP capture/test path. Mailpit is a development SMTP server with UI/API, not a production delivery provider. | Isolate it from public access and real recipients, test links/content and failure behavior, and separately smoke-test production DNS/TLS/provider delivery. |

Evidence: Resend Node/SMTP/domain docs, Nodemailer SMTP docs, Mailpit's maintainer README. [S18–S23]

### Domains, DNS and development

For real recipients, Resend requires a domain/subdomain you own and can verify, with the **exact provider-generated DKIM and SPF-related DNS records** (including return-path records as instructed). Prefer a dedicated transactional subdomain, such as `auth.example.com`, and plan DMARC. No application hosting choice removes these requirements. The built-in `onboarding@resend.dev` sender is for restricted testing to the account's own email address, not general user registration. A `vercel.app` deployment address is not an owned sending domain. Avoid overwriting unrelated inbound-mail MX records. [S20][S21]

Nodemailer does not verify a domain for you; sender/domain authorization is determined by the selected SMTP service. `transporter.verify()` checks connectivity/TLS/authentication, **not whether a particular From address will be accepted**. Use TLS with certificate verification: typically port 465 with implicit TLS, or port 587 with STARTTLS and `requireTLS: true`. Do not carry development self-signed-certificate exceptions into production. [S22]

Mailpit defaults to SMTP `1025` and UI `8025`. A host-run app can use a loopback-published SMTP port; a Dockerized app should address the Mailpit service on its private Docker network, not assume `localhost` is another container. No verified sending domain is needed for local capture. If production uses the Resend SDK, a development mail adapter can send the same generated text/HTML through Nodemailer to Mailpit; this does not test the production HTTP transport. [S23]

### Hosting constraints

**Vercel:** Prefer the HTTP API. SMTP is **not universally forbidden**: Vercel documents outgoing port 25 as blocked, with 465/587 available for Node-runtime SMTP. Nodemailer is a Node transport, not a portable Edge-runtime SMTP option. SMTP exchanges and connection pools have lifecycle/timeout hazards inside functions; do not assume a process or socket survives across invocations. Keep secrets server-side and configure Preview/Production separately. The Vercel guide's provider table calls Resend “HTTP-only,” but Resend's own current SMTP documentation explicitly supports SMTP; that table is not evidence that Resend lacks SMTP. [S19][S24]

Never start a bare untracked promise and return success expecting serverless execution to continue. For auth flows, dispatch must also avoid making account existence obvious through response timing. Use a supported request-lifecycle/background facility, or enqueue durably before returning a generic response. Vercel's `waitUntil` keeps work alive only within function execution limits; it is not a durable queue or automatic retry system. Do not copy Next.js `after()` examples into Nuxt without checking the actual Nitro/Vercel integration. The transport does not settle reliability requirements. [S4][S24][S25]

**Docker VPS:** A persistent Node/Nitro server can use either Resend HTTPS or provider SMTP, and can run a worker if durability is approved. Check the chosen VPS provider's outbound-port policy rather than assuming all providers allow SMTP. Keep PostgreSQL data/backups durable, terminate HTTPS at a correctly configured proxy, protect secrets, and manage upgrades/restarts. Running an outbound mail server yourself would add reputation, reverse DNS, abuse and queue operations; neither Nodemailer nor “Docker VPS” makes that a free delivery service. This report recommends a hosted transactional provider, not self-hosted internet mail. No particular VPS provider has been selected or tested.

No volatile free-tier prices were compared.

## 7. Supabase Postgres without Supabase Auth

Supabase documents each project as a full PostgreSQL database and provides a Drizzle/Postgres.js integration. Its Drizzle guide even permits disabling the Data API when using only Drizzle. Consequently a server-held Postgres connection string can support Better Auth's tables or custom tables without calling Supabase Auth or using the Supabase browser SDK. Auth users need not be rows in Supabase's `auth.users`; use the application's chosen auth user IDs consistently for notes and tags. [S26–S28]

Operational differences matter:

- **Vercel/functions:** Supabase recommends its shared transaction-mode pooler for short-lived/serverless connections. With Postgres.js/Drizzle, disable prepared statements (`prepare: false`), constrain per-instance connection pools and validate current driver/pooler limitations. “Transaction pooling” does **not** mean transactions are unavailable: it means session state cannot be assumed across transactions. The auth reset/revocation transaction must remain on one real database transaction. [S27]
- **Persistent VPS:** Prefer direct connections if the network supports the project's IP endpoint; the shared session pooler is an alternative for IPv4-only networks. Use the Dashboard's actual URI rather than constructing a pooler hostname. Use an appropriate migration connection rather than blindly reusing runtime transaction-pooler settings. [S27]
- **TLS:** Encrypt database traffic and configure certificate/hostname verification where supported. Supabase distinguishes `sslmode=require` encryption from `verify-full` server verification; do not equate them. Never expose the database password to Nuxt public runtime config. [S27]
- **Authorization:** Neither Better Auth nor an app-issued cookie automatically populates Supabase Auth JWT claims/`auth.uid()`. With server-only SQL, enforce owner-scoped queries and verified authentication in the app, using least-privileged database credentials. If the Data API stays enabled, separately secure its exposed tables/grants/RLS or keep auth tables unexposed. A privileged Postgres connection is not automatically constrained by browser-facing RLS policies. [S26–S28]
- **Local development:** Ordinary local PostgreSQL is sufficient if no Supabase-specific service is used. Review extensions, migrations, schema permissions and backups for local/production parity. Supabase as a database host is not a requirement to run its complete local Auth/Storage stack.

These are proposed choices, not approvals. The already accepted 30-minute/latest-only/single-use reset, generic forgot response, verification gate, session maximum and all-session revocation must not be quietly weakened to library defaults.

| **D9 — Google later:** does trusted Google verification satisfy the gate, can same-email accounts auto-link, what scopes/tokens are retained, and what public callback survives migration? | Trust a validated Google verified-email signal, require explicit linking to existing accounts, use provider+`sub`, request sign-in scopes only, and avoid unnecessary retained/offline tokens. Decide before enabling the provider; no Google implementation is authorized here. |
| **D10 — Public HTTP contract and cutover:** which request field names, status/error shapes, CSRF scheme, cookie attributes and migration login behavior are stable? | Approve a small app-owned contract separately from auth-library routes; include server enforcement/no-bypass and Set-Cookie propagation. Plan session invalidation at Laravel cutover unless compatibility is explicitly funded. |

## 9. Validation gate for a later implementation (not tests added by this report)

- Direct API access by anonymous and unverified users cannot read/write notes, tags or settings; a verified user cannot access another owner's data.
- Password boundaries include 14/15/128/129 code points, supplementary-plane characters, combining sequences, significant leading/trailing spaces, and chosen normalization vectors, identically across signup/login/change/reset and any future Laravel verifier.
- Reset at expiry, repeated redemption and **parallel** redemption have the required outcome. Issuing B makes A unusable even before B is redeemed, including concurrent issue/redeem and mail failures. Transaction failures do not leave a changed password with usable old sessions.
- Multiple devices and copied cookies: password change/reset revoke all prior sessions, no replacement stays active under the chosen policy, current logout does not revoke others, and session/cache/SSR behavior cannot bypass the database check. Race login against password change/reset.
- Known/unknown forgot requests have equivalent public outcomes; throttles work across instances/restarts and through application wrappers, and provider latency/errors do not trivially enumerate accounts.
- Deployed HTTPS cookies have verified HttpOnly/Secure/SameSite/path/expiry behavior; a hard lifetime does not become rolling; origin/CSRF/redirect controls are preserved behind the actual proxy.
- Mailpit captures working text/HTML links locally; production smoke tests verify sender DNS, TLS, scoped secrets, provider acceptance/error handling and lifecycle/durability behavior. Supabase pooler tests cover real multi-statement transactions and configured driver limits.

No dependencies were installed, application files changed, or runtime/security tests performed for this research-only task.

## 11. Mailtrap follow-up — superseding mailing recommendation

**Checked 2026-11-02.** This section supersedes the **Resend + Mailpit mailing recommendation** in §1/§6 and D7, and the Mailpit-specific suggested email check in §9; those earlier findings remain historical comparisons, not silent edits. **PostgreSQL + Drizzle are now confirmed for local and production use; Vercel versus VPS remains undecided. Zod is now required wherever application validation is needed**, including request/configuration validation, without weakening the accepted password semantics or silently trimming passwords. No generic Zod research, implementation, installation or tests are included. All existing auth/security requirements remain unchanged.

### Straight answer: Mailtrap is a reasonable, straightforward choice

**Recommend Mailtrap's Node/TypeScript SDK over HTTPS, with hosted Email Sandbox for development/Preview and Email Sending's Transactional Stream for production.** This can replace Resend + Mailpit with one SDK, the same message shape and one platform for captured test messages and production delivery logs. It removes the need to run a local mail container for the ordinary development workflow. It is simpler operationally **if internet-dependent, provider-hosted test mail is acceptable**—not because Sandbox is a production sender or because a mode flag verifies a domain. Keep the existing application-owned mail boundary and HTTP auth contracts. [M1–M3]

Mailtrap supports verification and password-reset messages as transactional mail. The provider transports the link; the application still issues/validates tokens, enforces the verification gate, and handles the accepted 30-minute, single-use, latest-only reset policy and all-session revocation. Do not choose the marketing/Bulk stream for these messages. [M3]

### Products and transports: what actually changes between environments

| Path | Development / hosted Email Sandbox | Production / Email Sending |
| --- | --- | --- |
| **`mailtrap` SDK: HTTP** | Explicit `sandbox: true` and `testInboxId`, plus a token authorized for that sandbox. Sends to `https://sandbox.api.mailtrap.io/api/send/{inbox_id}`; messages are captured, not normally delivered to recipients. No sending-domain verification is needed. | `sandbox: false`, no test inbox ID, and a separate domain-authorized sending token. Sends to `https://send.api.mailtrap.io/api/send`; From must use an approved, verified sending domain. |
| **Nodemailer: ordinary SMTP** | Connects to `sandbox.smtp.mailtrap.io`, using that sandbox's SMTP username/password, not an API token. | Connects to `live.smtp.mailtrap.io`, using the live sending SMTP credentials for the selected domain/stream. Reusing sandbox credentials will not turn capture into production delivery. |

Sources: current SDK implementation and Mailtrap API/SMTP docs. For SMTP, use a documented TLS-capable submission port, such as 587 with required STARTTLS and certificate verification; use each environment's complete configuration, not only a different password. [M1–M4][S22]

**Two easy-to-miss distinctions:**

- The SDK needs Node **22 or newer** at the checked current release, **v6.0.0**. Nodemailer is optional for direct `MailtrapClient.send()` usage. Mailtrap's separately exported **`MailtrapTransport` for Nodemailer calls the HTTP client internally**; it is not the ordinary host/port SMTP transport. Do not infer the network protocol from “Nodemailer” alone. [M1]
- SDK `sandbox` defaults to **false**. A missing/misparsed environment flag must not silently enable live mail in development/CI. Validate mode explicitly with Zod and keep production sending credentials unavailable outside production. A sandbox success is not proof of live sender authorization or inbox delivery. [M1–M3]

### Actual prerequisites and deployment fit

1. **Hosted Sandbox:** Mailtrap access, a sandbox, its API authorization/inbox ID (or its distinct SMTP configuration), outbound internet, and acceptable test-data access/retention. Keep forwarding disabled for safe capture; Sandbox supports optional forwarding, so “sandbox” is not permission to use real production accounts or secrets. [M2][M6]
2. **Production:** an owned sending domain/subdomain and DNS control; a matching From address; Mailtrap's required domain DNS records verified; sender information and compliance approval; and sending authorization scoped to that domain. Current Domain Setup documents verification/DKIM/tracking CNAMEs and a DMARC TXT record; use the records actually generated for the domain rather than copying a generic SPF/DNS example or overwriting existing mail records. The documentation also asks that owned domains linked in emails be added/verified—relevant if the app's auth-link domain differs from its sender domain. Demo-domain sending is restricted to the account's registered address, not general users. DNS and compliance can delay readiness; Sandbox working does not bypass either. [M5]
3. **Vercel:** the HTTP SDK is suitable in a **compatible Node runtime**, not an assumed Edge runtime; the client imports Node HTTP/HTTPS modules. Vercel offers compatible Node versions and Mailtrap documents a Vercel integration. That integration can populate environment variables, but does not implement Nuxt auth hooks, templates, Zod validation or reliable dispatch. Production/Preview secrets and sandbox modes still need explicit separation. SMTP is also possible in Node on allowed ports, but Vercel blocks port 25 and recommends HTTP. [M1][M7][S24]
4. **Docker VPS:** the same HTTP SDK works on supported Node with HTTPS egress. Nodemailer SMTP is also viable when the chosen VPS network permits the provider's submission port. Neither requires running a public mail server. Hosting remains a separate decision; choosing Mailtrap now need not force Vercel or a VPS. A future Laravel backend can retain Mailtrap via SMTP or its official PHP SDK rather than preserving the Node package. [M3][M4]

Keep API/SMTP secrets in server-only environment/configuration, never Nuxt public runtime config, browser bundles, git or CI artifacts. Use separate tokens with only necessary resource permissions for test versus sending, and sandbox read access only where CI inspection needs it; avoid account-wide admin access for the runtime. Provider error causes can include request context: sanitize logs, and do not log reset URLs or put bearer tokens in categories/custom variables. Exclude verification/reset links from click tracking (Mailtrap documents `data-mt-no-track`) or disable tracking for auth mail. [M1][M6][M10]

### Retries, idempotency and expiring reset links

**Do not claim automatic exactly-once email sending.** The inspected v6.0.0 SDK makes one Axios POST with a **10-second timeout** and rethrows errors; it contains no automatic send-retry/durable-queue mechanism. The checked transactional API reference and SDK expose no documented provider idempotency-key contract. Arbitrary email `headers`, custom variables or a Message-ID are not evidence of server-side deduplication. In contrast, Resend explicitly documents optional idempotency keys with a 24-hour window—a concrete retry ergonomics advantage of the earlier choice. Mailtrap remains reasonable if this limitation is accepted; do not assume an undocumented guarantee. [M1][M3][M8]

For a later implementation, distinguish an explicit rejection from an **ambiguous timeout after provider acceptance**. Bounded backoff can handle transient failures/rate limiting; invalid content, credentials or domain permissions need correction rather than blind retries. A timeout retry may duplicate a message. Mailtrap's own delivery retries after a soft bounce, or queuing when sending limits are reached, are separate from application-to-provider submission and can delay arrival beyond the token's lifetime. Successful submission/message IDs are not proof of inbox delivery. [M8][M9]

A retry of one dispatch should reuse its existing message/token, not mint another reset token and repeatedly invalidate earlier emails. Before application retries, stop obsolete/expired dispatches; never extend the 30-minute expiry merely because email was delayed. A genuinely new reset request must still invalidate its predecessor immediately. Already accepted older emails can arrive later, but their links must fail the database check. Provider deduplication, even where available, cannot enforce these auth invariants or atomically commit email with PostgreSQL. **D8 remains open:** choose lifecycle-tracked best effort versus durable dispatch/outbox, bounded retry/monitoring expectations, and the user recovery path when the newest email fails. Keep the forgot response generic in either case. On Vercel, an untracked promise is unsafe and `waitUntil` is not durable storage. [M8][M9][S24][S25]

### Local/CI ergonomics and remaining decisions

- **Hosted Mailtrap Sandbox + live Mailtrap:** one SDK/send shape and shared inspection workflow; useful for developers, reviewers and bounded CI integration checks. Network availability, service limits and hosted storage/access to test email are additional dependencies. Use synthetic accounts, isolated sandboxes or run-specific message correlation, bounded polling of the Sandbox API to inspect text/HTML/links, and cleanup without deleting another parallel run's mail. Disable forwarding and keep live tokens out of untrusted PR jobs. This tests capture and application link semantics, not production DNS, recipient delivery or real mailbox filtering. [M2][M3][M6]
- **Local Mailpit + production provider:** adds a local service and usually a separate SMTP dev transport when production uses HTTP, but works offline, keeps captured mail local and supports isolated CI without cloud credentials. Keep it if those properties outweigh the unified SDK workflow; it is **optional, not required** with hosted Mailtrap. Current Mailtrap docs also offer a separate **Mailtrap Local** SMTP/UI/API capture tool; this is not the hosted SDK's `sandbox: true` endpoint or automatic offline compatibility. It need not be adopted to choose Mailtrap Sending. [S23][M11]
- **Recommended test split for later authorization:** offline mocked mail boundary for routine unit tests, selected hosted Sandbox integration checks, then a controlled production delivery smoke check after domain approval. No tests or real emails were run here.

**Decision summary:** provider choice can reasonably be **Mailtrap**. Recommend SDK HTTP + hosted Sandbox + production Transactional Sending. Confirm (a) acceptance of cloud test-mail storage/network dependency versus keeping local capture, (b) sending/link domains, DNS operator, sender identity and compliance readiness, (c) production host with supported Node, and (d) D8's delivery/retry guarantees without a documented Mailtrap idempotency contract. Zod and PostgreSQL/Drizzle are now requirements, not reopened alternatives. No auth-policy change or implementation is authorized by this recommendation.
