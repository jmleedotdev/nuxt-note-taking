# Registration slice (#2)

## Run locally

Requires Node 22+, pnpm, and Docker/Compose. Any valid email address is accepted;
use reserved example domains for testing. Development email is captured by Mailtrap
Local rather than delivered to recipients; no Mailtrap account, API key, inbox ID,
or outbound internet is needed after the image is pulled.

1. `pnpm install`
2. `docker compose up -d --wait`
3. Copy `.env.example` to `.env`, generate a unique auth secret, and use
   `MAIL_MODE=local` with `MAILTRAP_URL=http://127.0.0.1:3550`.
   Remove obsolete `MAILTRAP_API_KEY` / `MAILTRAP_INBOX_ID` settings. Never copy
   production sending credentials into development, Preview, or CI.
4. Set `DATABASE_URL` in `.env` to your application database. The example matches
   the included Compose service; adjust it if you change the service credentials
   or port. Nuxt dev reads `.env`; `drizzle.config.ts` explicitly loads it for
   Drizzle Kit using dotenv. Run `pnpm db:migrate` to apply generated migrations.
   An exported `DATABASE_URL` takes precedence over `.env`; missing/empty connection
   settings make migration fail rather than select a default database.
   `pnpm db:generate` only needs the schema files, not a database connection.
5. `pnpm dev`; open `/signup`.
   Authentication-aware routing for `/` is deferred; visit `/signup` directly.
6. Open `http://127.0.0.1:3550` to inspect captured verification emails and follow
   their links. The app still runs on the host; PostgreSQL and Mailtrap run in Docker.

`docker compose down` retains both the local database and captured mail.
`docker compose down -v` deletes both volumes and their data. This is deliberately
local-only infrastructure, not a deployment design. Mailtrap's API/UI has no
authentication and is published only on `127.0.0.1:3550`; its SMTP port is not
published. Compose waits for PostgreSQL's healthcheck, but Mailtrap has no built-in
HTTP readiness healthcheck; wait for the inbox UI/API to respond after startup.
Migration files are generated by Drizzle Kit, committed/reviewed as SQL, and applied
by `drizzle-kit migrate` for the application database. The isolated test harness
continues applying them programmatically with Drizzle's migrator.
Runtime never auto-migrates.
The database client lives in `server/db/client.ts`. Schemas are grouped by feature
in `server/db/schema/auth.ts` and `server/db/schema/registration.ts`, without a
barrel file; Drizzle Kit discovers `server/db/schema/*.ts`. Generated SQL migrations
and Drizzle metadata live in root `drizzle/`. All migration runners use that folder.
Better Auth tables are `user`, `session`, `account`, and `verification`, without
an `auth_` prefix. The initial migration creates these names directly; there is no
separate rename migration. All creation, update, and expiration timestamps use
PostgreSQL `timestamptz` (`withTimezone: true`); browser-local display formatting
is a separate UI concern. Precision is left at PostgreSQL's default.
An earlier local database must be reset (only if disposable) or updated separately
before using this baseline. Rewriting the initial migration does not update
existing table names or column types.

## Tests and isolation

The app and test harness both use **`DATABASE_URL`**; environment selection is
explicit rather than encoded in separate variable names.

- Copy `.env.test.example` to `.env.test.local` and set `DATABASE_URL` to a
  **disposable test PostgreSQL cluster** whose role has CREATEDB. These local
  files are ignored by Git; both example templates are tracked.
- The test harness loads `.env.test.local` only when `DATABASE_URL` has not been
  supplied directly. It never loads or falls back to the application's `.env`.
  Missing/empty test configuration fails before a database connection is opened.
- A supplied `DATABASE_URL` takes precedence, including in CI. If you previously
  exported the application's URL, run `unset DATABASE_URL` before using the local
  test file. The URL is the operator's responsibility: never target production.
- The example can use the local Compose cluster, but does not require it. Use a
  separate test cluster/role when you need stronger separation from development.

The harness creates a cryptographically random `notes_test_*` database, applies
actual migrations, and passes its URL to the test process as `DATABASE_URL`,
overriding the cluster connection for that process. It drops only that generated
database in `finally`; it never truncates the database named by the supplied URL.
A hard kill can leave a test database; remove only your abandoned `notes_test_*`
database after checking no test process is using it.

- `pnpm test`: complete Vitest suite, including real Nuxt HTTP/PostgreSQL.
- `pnpm test:http`: focused HTTP suite. Its real cooldown-expiry check waits
  30 seconds rather than replacing PostgreSQL time or weakening the tested limit.
- `pnpm test:browser`: Playwright desktop, tablet, and mobile Chromium, using the
  Nuxt-aware fixture. Port 3000 must be available. Browser runs use the same
  isolated database/migrations and memory sender, with unique synthetic recipients.
- `pnpm test:mail`: opt-in real-transport smoke test, using a separate Vitest config.
  Start Mailtrap first with `docker compose up -d mailtrap`. It uses the same isolated
  PostgreSQL harness, but overrides the Nuxt sender to Local, searches only its unique
  synthetic recipient, checks captured HTML/text and the real verification callback,
  and deletes only its own captured messages. It never clears the shared inbox.
  `MAILTRAP_URL` may select another loopback HTTP origin; the default is port 3550.
- `pnpm typecheck` and `pnpm lint`.

The memory sender replaces transport only; Better Auth issues real tokens and
uses real PostgreSQL. A capture/failure-control HTTP handler is **injected only
by the HTTP test configuration**, outside `server/`; it is absent from ordinary
development and deployment builds. The production adapter factory rejects memory
mode unless `APP_ENV=test`.

Test runner commands must go through the isolation script for the HTTP/browser
projects. The existing unit and Nuxt-environment projects remain usable separately.
No Mailtrap checks run during routine tests. `test:mail` exercises the pinned
Mailtrap Local image explicitly; it is not part of the default Vitest projects.
There is no live production sender or hosted Preview mail adapter in this slice.

## Public HTTP contract

All mutation endpoints require JSON and an exact configured Origin; missing Origin,
cross-site Fetch Metadata, and foreign Origin are rejected. Cookies are forwarded
to the server API, but these registration operations **must never issue sessions**.
The underlying Better Auth HTTP handler is not mounted. Login, reset, change, and
other library routes cannot bypass policy; they return 404.

- `POST /api/registration`: `{ email, password }`.
- `POST /api/registration/resend`: `{ email }`; generic known/unknown outcomes.
- Both accepted responses: HTTP 202 `{ status: "check-email", resendAfter: 30 }`.
- Invalid fields: HTTP 422 `{ error: { code: "VALIDATION", fields: { ... } } }`.
- Limit: HTTP 429 `{ error: { code: "RATE_LIMITED" }, retryAfter }` plus Retry-After.
- Wrong Origin/content type: 403 FORBIDDEN_ORIGIN. Malformed JSON: 400
  INVALID_REQUEST. Body over 4096 bytes: 413 REQUEST_TOO_LARGE.
- Unexpected registration failure: sanitized 503 REGISTRATION_UNAVAILABLE.
  The UI preserves the entered email and offers retry. Recovery without shared
  email context follows the login redirect described below.
- Verification links use `GET /api/registration/verify?token=...`; the small
  bootstrap callback maps success to a fixed `/login?verified=1` redirect,
  invalid/expired to `/check-email?invalid=1`, and sets no cookie. Full login,
  verification results, protected shell, and logout are issue #3. In particular,
  the login destination is not implemented by #2.

Responses never include a library user/account, credential hash, or token.
Passwords remain in local form state only until success; neither passwords nor
email are persisted in localStorage. Check-email email/cooldown state is ephemeral;
there is no email query parameter or persistent browser storage.

**Superseding confirmation-screen decision:** `/check-email` displays the submitted
email as read-only text, with no email input or form. Its **Send again** button
requests a new verification email for that same address. It is disabled while
pending or cooling down and displays `Send again (15s)` during the 30-second
cooldown. Accepted resends show no success message and clear any previous error;
failures still show error feedback. API outcomes remain generic; accepting a
request does not guarantee delivery.

Without email context (including after a full reload), an ordinary visit redirects
to `/login` with history replacement. `/check-email?invalid=1` without email context
instead preserves the invalid/expired-link message and offers **Back to login**,
without a resend button. When email context exists, the page retains its resend
action and **Back to sign up** link. The login page itself remains issue #3.
Server rate limits remain authoritative even if the client clock is advanced or
its temporary cooldown state is lost.

## Exact password semantics

**Superseding review decision:** the user approved replacing parent #1 and issue
#2's original Unicode/passphrase policy with **8–128 printable ASCII characters,
excluding spaces**. This document records that explicit change; the historical
research describes the earlier policy and is not the current password contract.

- The minimum was subsequently changed from 15 to 8 characters by explicit user
  request to match the signup design. The maximum remains 128; other character
  restrictions are unchanged.
- Allowed characters are ASCII `U+0021` through `U+007E`: English uppercase and
  lowercase letters, digits, and punctuation/symbols.
- Spaces, tabs, line breaks, other control characters, and all non-ASCII
  characters are rejected. They are never trimmed, converted, or silently removed.
- No composition requirements: letters-only, digits-only, and symbols-only
  passwords are accepted if they meet the length limit.
- Password managers, autofill, and paste remain supported.
- The shared Zod schema enforces this policy in the form, HTTP request, hashing,
  and credential verification. Better Auth's length bounds are also 8–128.
  No other password-writing library endpoint is reachable. Reuse the schema for
  login, change, and reset in later slices.
- Hash format remains `scrypt-raw-v1:<salt-hex>:<key-hex>`: Node scrypt defaults
  N=16384, r=8, p=1; random 16-byte salt encoded as a UTF-8 hex string; 64-byte key;
  password encoded directly as UTF-8. Verification uses constant-time comparison.
  Accepted ASCII passwords have no Unicode normalization ambiguity.
  No Laravel hash compatibility is promised.
- Existing ASCII credentials remain compatible. Earlier local-development
  passwords containing spaces/non-ASCII are now rejected; recreate those
  synthetic accounts or provide recovery in a later slice. No stored credential
  is silently rewritten. A rollout to existing real users would require a
  deliberate migration/recovery plan.

HTTP tests cover 7/8/128/129-character boundaries, letters/digits/symbols,
rejection of spaces/control/non-ASCII input, all four numeric abuse ceilings,
forged proxy headers, concurrency, and real cooldown expiry. Focused hash/verify
tests cover the complete allowed ASCII range, rejected character categories,
round trips, and case/symbol sensitivity. Browser tests exercise invalid
space-containing input, preserved email, and valid ASCII signup.
These credential checks should also be exercised through issue #3's real login
endpoint when it exists.

## Abuse control and trusted IPs

Both signup and resend share PostgreSQL fixed-window counters:
**20 attempts/IP/hour**, **5 attempts/email/hour**, **1 attempt/email/30 seconds**,
and **500 attempts globally/hour**. Validated submissions consume these limits,
including denied attempts; malformed/invalid fields never reach expensive hashing.
Every relevant row is atomically incremented via INSERT ON CONFLICT inside one
transaction, with stable lock ordering. All instances using the database and secret
share the same counters. Retry-After is the maximum remaining denied window.

Email is lowercased (not trimmed), validated for syntax, and limited to 254
characters in both forms and requests. There is no recipient-domain allowlist:
registration and resend accept any valid address, while Mailtrap Local captures
messages without delivering them externally. Emails and IPs are stored only as
keyed HMAC digests in the limit table, not raw identifiers. Keep the auth secret stable across
instances. Expired counters reset atomically; periodically remove expired rows
(`DELETE FROM registration_limit WHERE expires_at < now()`) for storage hygiene.

Direct connections use the TCP peer address. Ignore X-Forwarded-For. Only when the
actual peer exactly matches `APP_TRUSTED_PROXY_IP` may a single valid `X-Real-IP`
be used. The controlled proxy must **overwrite**, not append or pass through, that
header, and direct access to the application must be prevented in deployment.
No deployment-specific proxy is presumed. IPv4/IPv6 accepted; deployers must
validate their ingress and IPv6 aggregation policy before exposure.

## Mail lifecycle, safety, and limitations

**Superseding review decision:** Mailtrap Local replaces hosted Sandbox for local
development. The hosted SDK and credential settings are removed; remote Preview
and production mail remain undecided rather than keeping speculative adapters.

The server-only MailSender accepts application text/HTML messages. Compose pins
`mailtrap/mailtrap-local:0.4.1`; the adapter posts JSON to `/api/v1/ingest` with
native fetch, a five-second timeout, no redirects, and no automatic retries. It
requires HTTP 201 plus a nonempty capture ID. Zod requires an explicit mail mode
and, for Local, an HTTP origin on `localhost`, `127.0.0.1`, or `[::1]`, without a
path, query, or credentials. Memory mode is test-only; no live fallback exists.

The direct ingest endpoint is internal/test-oriented upstream, not the hosted
SDK API. A release update needs a fresh contract smoke test. Local 0.4.1 requires
an explicit empty raw blob for structured HTTP capture; omitting it returns 422.
HTML/text and envelope addresses are captured, but raw SMTP/MIME source is not
synthesized. This verifies application mail and links, not SMTP/MIME fidelity or
recipient deliverability.

The named `mailtrap-data` volume persists SQLite inbox data and its local key.
Captured verification links are sensitive: keep this unauthenticated developer
inbox private and do not use real accounts. Relay, cloud upload/mirroring, and
webhooks are left unconfigured. These features can be enabled through the tool's
UI; localhost publishing and empty settings are not network-enforced no-egress
isolation. Do not add live credentials or configure outbound connections.
Production remains unsupported until a provider/deployment is selected.

Signup awaits submission within the auth request. Resend uses H3/Nitro
`event.waitUntil`, not a bare promise, so account/provider latency cannot change the
generic public response. Mail failures log fixed messages only; never log the
exception, request, email, token, URL, password, or provider credentials.
Disable access-log query capture on verification URLs and configure observability
redaction before deployment. Auth mail disables click tracking with
`data-mt-no-track`; disable tracking at the provider account too.

There are **zero automatic retries**. An ambiguous timeout might already have been
accepted, so no blind retry mints a token or extends expiry. A deliberate,
rate-limited resend is a new verification authorization, not a retry of a previous
dispatch; verification does not require latest-only/single-use behavior.
Each generated link expires in one hour. Provider acceptance is not delivery;
process crashes can lose an attempt; provider delays can outlive expiry. There is
no durable queue, outbox, exactly-once guarantee, or production readiness claim.
